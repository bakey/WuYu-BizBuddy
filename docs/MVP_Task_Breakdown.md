# 无隅 BizBuddy MVP 任务拆解与分工建议

> 依据：`docs/MVP_PRD.md`（产品范围）、`docs/MVP_Client_Tech_Design.md`（技术架构）
> 现状：客户端 Electron 原型已完成（`client/`，UI + mock 服务层，mac/win 安装包可构建）
> 周期：12 周（2.5~3 个月）

---

## 1. 模块总览

```
┌─────────────────────────────────────────────────────────────┐
│ A. 桌面壳（Electron）        E. 前端 UI（Vue3）               │
│ B. Agent 内核（dsh 集成）    F. 管理后台 Web                  │
│ C. 文档/RAG 服务（sidecar）  G. 模型接入与配置                │
│ D. DCS 采集服务              H. 测试与发布                    │
└─────────────────────────────────────────────────────────────┘
```

建议投入 **4~6 人**，分工矩阵见第 4 节。

---

## 2. 模块拆解（含交付物、依赖、验收标准）

### A. 桌面壳（Electron）

| 项 | 内容 |
|----|------|
| 任务 | 主进程完善：子进程编排（内核/sidecar/collector 的启动、守护、崩溃重启）；API Key 安全存储（safeStorage）；自动更新（electron-updater）；首次启动引导流程；macOS 签名公证 / Windows 签名 |
| 交付物 | 可分发的 mac dmg / win exe 安装包；自动更新通道 |
| 依赖 | E（UI）、B/C/D（子进程就绪后才能联调编排） |
| 验收 | PRD 流程 0：下载 → 安装 → 首次引导配置模型 → 完成首次问答 ≤ 30 分钟；杀进程后自动重启子服务 |
| 估时 | 4 周（可与 E 并行） |

### B. Agent 内核（dsh 集成）

| 项 | 内容 |
|----|------|
| 任务 | W1 spike（嵌入可行性/插件机制/会话日志）；`AgentKernel` 适配层接口；Model 插件（OpenAI 兼容端点）；Tool 插件（doc_search / ts_query / ts_list，HTTP 调 sidecar）；Skill 插件（扫 `skills/` 目录 SKILL.md，移植现有 `skill_package.py` 逻辑）；安全环保专家 Agent 的声明式定义（prompt 用 jinja2 模板）；会话日志 → 轨迹观测数据接口 |
| 交付物 | 内核 utility process + 插件集 + 适配层 |
| 依赖 | G（模型配置协议）、C/D 的 API 契约（先按 mock 契约开发） |
| 验收 | 提问 → 自动调 doc_search（涉及时序再调 ts_query）→ 流式回答带引用；轨迹日志完整记录模型/工具调用 |
| 估时 | 5 周（W1 spike 是 go/no-go 关口） |

### C. 文档 / RAG 服务（Python sidecar）

| 项 | 内容 |
|----|------|
| 任务 | 从现有 `backend/` 裁剪：去 Postgres/多用户鉴权，元数据改 SQLite，向量库换嵌入式 LanceDB；文档解析（PDF/Word/Excel/图片）、切片、BGE Embedding、rerank；索引管理 API（状态、重建、删除同步）；PyInstaller 打包单文件 |
| 交付物 | sidecar 可执行文件 + HTTP API（仅 loopback） |
| 依赖 | 无（可最先启动）；B/E/F 都消费它的 API |
| 验收 | 上传文档 → 状态流转（解析中→已入知识库）；提问能命中引用；删除文档后检索不到 |
| 估时 | 4 周 |

### D. DCS 采集服务

| 项 | 内容 |
|----|------|
| 任务 | OPC UA 采集（`asyncua`，MVP 只做一个协议）；点位配置热加载（客户端与数据源动态关联）；时序数据本地存储（SQLite/Parquet，7 天滚动）；心跳与延迟上报；`ts_query`/`ts_list` API（供内核工具调用）；数据源 CRUD + 测试连接 API（供管理后台） |
| 交付物 | collector 可执行文件 + 时序 API |
| 依赖 | C 的存储约定；需要一台可连的 OPC UA 测试服务（可用公开仿真器） |
| 验收 | PRD 流程 3：管理员添加数据源 → 测试连接通过 → 客户端上线有心跳 → 对话中能查到点位数据 |
| 估时 | 3 周 |

### E. 前端 UI（Vue3 桌面端）

| 项 | 内容 |
|----|------|
| 任务 | 把 `client/` 原型的 mock 层替换为真实调用（mock/api.ts 的接口签名就是契约，UI 不动）；对话流式渲染联调；断网/模型未配置提示；文档上传真实进度；异常态（解析失败、超时、空结果） |
| 交付物 | 桌面端三个页面（新对话/能力/数据库） |
| 依赖 | A（壳）、B（对话流）、C（文档 API） |
| 验收 | PRD 流程 1/2 端到端可用；回答引用可点击定位文档 |
| 估时 | 3 周（原型已完成，主要是联调） |

### F. 管理后台 Web

| 项 | 内容 |
|----|------|
| 任务 | 按 `wuyu_product_mvp_admin.html` 实现：文档与索引（概览 + 表格 + 重建索引）、DCS 接入（数据源 CRUD + 测试连接 + 点位批量导入）、接入客户端（心跳列表）、模型配置、轨迹观测（读内核会话日志）；简单管理员登录 |
| 交付物 | Web 管理端（可复用 client 的技术栈，独立小应用） |
| 依赖 | C/D/B 的管理 API |
| 验收 | 管理员能独立完成：管理文档索引、接入一个 DCS 源并看到客户端上线、配置模型、查看轨迹 |
| 估时 | 4 周 |

### G. 模型接入与配置

| 项 | 内容 |
|----|------|
| 任务 | OpenAI 兼容端点配置（CRUD + 测试连接）；Key 的主进程安全存储与注入；默认模型切换；流式调用封装（供内核 Model 插件使用） |
| 交付物 | 模型配置模块（主进程 + 内核插件协议） |
| 依赖 | A（Key 存储）、B（插件消费） |
| 验收 | 配置 DeepSeek 端点后对话可用；Key 不出现在渲染进程和日志中 |
| 估时 | 1.5 周 |

### H. 测试与发布

| 项 | 内容 |
|----|------|
| 任务 | 端到端冒烟（扩展现有 `npm run smoke`）；双平台安装/卸载/升级测试；性能基线（问答 < 10s / 时序 < 20s）；内测组织（≥3 个安环场景）；打包签名与分发渠道 |
| 交付物 | 测试报告 + 发布包 |
| 依赖 | 全部模块 |
| 验收 | PRD 第 9 节成功指标全量过一遍 |
| 估时 | 2 周（最后集中，前期按需参与） |

## 3. 模块间接口（开发前必须先对齐）

| 接口 | 提供方 → 消费方 | 说明 |
|------|----------------|------|
| 对话流式协议 | B → E | 事件流：检索中/文本分片/引用/完成/错误 |
| `doc_search` / 文档管理 API | C → B、E、F | HTTP，路径与字段在 W2 前冻结 |
| `ts_query` / `ts_list` / 数据源 API | D → B、F | 同上 |
| 轨迹日志读取 | B → F | 会话日志的查询接口 |
| 模型配置协议 | G → B | 主进程注入，含测试连接结果格式 |
| 子进程生命周期约定 | A → B/C/D | 端口分配、健康检查、崩溃重启策略 |

> 建议 W1 结束前用一份 `docs/接口契约.md` 冻结这些接口（mock 层 `client/src/mock/api.ts` 已包含对话与文档的雏形，可直接演进）。

## 4. 分工矩阵建议

| 人员 | 负责模块 | 说明 |
|------|----------|------|
| 1 号（桌面/前端） | A + E | Electron 壳 + 桌面 UI 联调，原型作者顺手 |
| 2 号（Agent 内核） | B + G | dsh 集成、插件、模型接入，需要 Node/TS 能力最强的人 |
| 3 号（RAG 服务） | C | Python，熟悉现有 backend 的人最优 |
| 4 号（数据接入 + 后台） | D + F | Python（采集）+ 前端（管理后台），工作量可平衡 |
| （可选）5 号 | H + 各模块支援 | 测试、发布、文档 |

## 5. 排期（对齐里程碑）

| 周 | 全员事项 |
|----|----------|
| W1 | **接口契约冻结 + B 的 dsh spike（go/no-go）**；C/D 动工 |
| W2-W5 | C/D/G 完成；A 子进程编排联调；B 内核插件开发；F 动工 |
| W6-W8 | B 内核完成；E 联调对话主链路；F 三个 Tab 完成 |
| W9-W10 | 端到端联调（流程 0~3 全通）；H 介入测试 |
| W11-W12 | 打包签名、内测、修问题、发布 |

**关键路径**：B（dsh spike → 内核）→ E 联调 → 端到端。W1 的 spike 结论若是否定，回退方案是把现有自研 executor 包进适配层（工作量 +1~2 周，需提前告知管理层）。

**最大外部风险**：macOS 公证 / Windows 签名证书申请周期长，建议 W1 就启动申请。
