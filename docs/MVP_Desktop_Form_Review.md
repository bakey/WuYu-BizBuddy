# 无隅 BizBuddy：Codex / Claude Code 形态下的产品建议

## 1. 形态对齐

你提到最终形态类似 **Codex / Claude Code**，这对产品定位非常关键。这类产品的共同特征是：

- **本地运行**：安装在用户电脑上，数据默认留在本地
- **Agent 驱动**：不是简单的 Chatbot，而是能规划、调用工具、执行任务的 Agent
- **上下文感知**：自动感知当前工作目录、文件、项目结构
- **代码/文件操作**：能读写文件、执行命令、生成报告
- **终端式交互**：以对话流为主，但允许查看和确认中间过程

把 BizBuddy 做成这种形态，意味着它不应该是一个“面向生产管理人员的 Web 仪表盘”，而应该是一个**面向工业技术人员的本地智能工作台**。

---

## 2. 产品形态调整建议

### 2.1 从“Web 仪表盘”转向“本地工作台”

当前原型的信息架构：

```
新对话
专家
数据库
模型配置
轨迹观测
```

这个结构更像一个 SaaS 产品的后台管理系统。如果做成 Codex / Claude Code 形态，建议调整为：

```
┌─────────────────────────────┐
│  会话区（主要界面）           │
│  └── 用户与 Agent 对话流       │
│  └── 中间过程可视化（可收起）    │
│  └── 结果文件 / 报告 / 图表      │
├─────────────────────────────┤
│  上下文区（左侧或右侧抽屉）      │
│  └── 当前项目目录 / 已选文档     │
│  └── 已接入数据源状态           │
│  └── 常用命令 / 快捷操作        │
├─────────────────────────────┤
│  设置区（右上角齿轮）           │
│  └── 模型配置                 │
│  └── 数据存储路径              │
│  └── 权限与安全               │
└─────────────────────────────┘
```

### 2.2 对话交互模式

Codex / Claude Code 的核心交互模式：

1. **用户输入自然语言**
2. **Agent 生成计划**（Plan）
3. **Agent 调用工具执行**（Tool Calls）
4. **Agent 返回结果和证据**
5. **用户确认或修正**

在 BizBuddy 中，这意味着：

- 用户说：「分析二号线最近能耗异常」
- Agent 自动拆解：
  1. 检索知识库中关于二号线能耗的文档
  2. 查询后台 DCS 中最近 24 小时的能耗趋势
  3. 对比 SOP 中的正常范围
  4. 生成分析结论和引用
- 用户可以直接在对话中查看中间步骤，也可以一键收起

### 2.3 专家角色调整

当前原型中的“专家选择器”在 Codex / Claude Code 形态下可以简化：

- **默认只有一个主 Agent**：无隅工业助手
- **后台根据问题自动路由到不同能力域**：
  - 生产分析域
  - 设备维护域
  - 安全环保域
- 用户不需要显式选择专家

这样做的好处：

- 降低用户心智负担
- 更像一个真正的 Agent
- 后台仍然可以保留多个 Agent 编排逻辑

## 3. 本地数据与云端 LLM 的分工

既然客户允许联网调用云端 LLM，那么本地和云端的分工应该是：

| 层级 | 职责 | 数据是否离开本地 |
|------|------|----------------|
| 本地 | 文档存储、向量索引、对话历史、时序数据缓存、文件操作 | 否 |
| 云端 | 大模型推理、Embedding 计算、Rerank 重排 | 是（仅 query 和检索片段） |

### 3.1 本地必须做的事

1. **文档解析与存储**
   - 上传文档后本地解析
   - 生成向量索引
   - 存储在本地目录（如 `~/Library/Application Support/BizBuddy`）

2. **对话历史**
   - 所有对话记录本地保存
   - 支持导出 / 删除

3. **时序数据缓存**
   - 从企业内网拉取 DCS 数据后本地缓存
   - 支持离线分析最近 N 小时数据

4. **文件操作**
   - 读取本地文件作为上下文
   - 生成报告、图表并保存到本地

### 3.2 云端必须做的事

1. **LLM 推理**
   - 所有大模型调用走云端 API
   - 本地只做 prompt 组装和结果解析

2. **Embedding / Rerank**
   - 可选：本地小模型或云端 API
   - 如果客户允许，直接用云端 API 更简单

### 3.3 隐私边界

需要明确告诉用户：

- 上传到云端的内容：用户 query + 检索到的文档片段 + 必要的上下文
- 不上传的内容：原始文件全文、本地目录结构、完整的时序数据

## 4. 与当前原型的差异

### 4.1 需要新增的能力

| 能力 | 说明 |
|------|------|
| 本地项目目录感知 | 能感知当前工作目录，自动关联相关文件 |
| 文件读写 | 能生成报告、图表、CSV 并保存到本地 |
| 命令执行 | 可选：在确认后执行本地命令（如打开文件、运行脚本） |
| 中间过程可视化 | 显示 Plan、Tool Calls、引用来源 |
| 本地知识库管理 | 文档、向量索引、对话历史都在本地 |

### 4.2 需要简化的部分

| 当前设计 | 调整建议 |
|----------|----------|
| 数据库页作为独立模块 | 改为上下文区的一个 Tab，管理当前项目文档 |
| 三个独立专家 | 后台保留三个 Agent，前端统一为一个助手入口 |
| 轨迹观测页 | 保留，但嵌入到对话页的“查看过程”按钮中 |
| 模型配置页 | 保留，但改为设置弹窗，不占主导航 |

## 6. 关键交互设计建议

### 6.1 输入区

支持两种输入方式：

1. **自然语言**：直接提问
2. **命令模式**：`@` 引用文件、`#` 引用数据源

示例：
- `@二号磨机检修SOP.pdf 这份文档对轴承温度有什么要求？`
- `#二号线DCS 最近 24 小时能耗为什么升高？`
- `结合 @SOP 和 #DCS 分析二号线能耗异常`

### 6.2 中间过程展示

Codex / Claude Code 的核心体验是让用户看到 Agent 在“思考”和“执行”。建议：

- 默认收起，点击展开
- 展示：
  - 计划（Plan）
  - 工具调用（Tool Calls）
  - 检索到的文档片段
  - 查询到的时序数据
  - 最终结论

### 6.3 结果输出

支持多种输出形式：

- 文字回答
- Markdown 报告
- CSV / Excel 表格
- 图表（本地生成 PNG / SVG）

## 7. 对现有代码的影响

当前代码是 FastAPI + PostgreSQL + Vue 3 的 Web 架构。如果要转向桌面应用，需要：

### 7.1 后端调整

- **数据库**：PostgreSQL → SQLite / DuckDB
- **向量库**：pgvector → Chroma / sqlite-vec
- **认证**：移除 rswaste-platform 认证，改为本地用户或无需登录
- **文件存储**：数据库 BLOB → 本地文件系统
- **DCS 接入**：由后台服务改为可选的内网 API 调用

### 7.2 前端调整

- **打包方式**：Vite 构建 → Tauri / Electron 桌面应用
- **路由**：Vue Router → 本地状态管理
- **文件操作**：通过 Tauri API 读写本地文件

### 7.3 部署方式

- **macOS**：`.dmg` / `.app`
- **Windows**：`.msi` / `.exe`

---

## 8. 总结

如果 BizBuddy 要做成 Codex / Claude Code 形态：

1. **产品定位**：本地工业智能工作台，不是云端 SaaS
2. **交互方式**：Agent 驱动，用户自然语言输入，系统自动规划和执行
3. **数据边界**：本地存储文档和对话，云端只负责 LLM 推理
4. **专家设计**：后台保留多 Agent 编排，前端统一为一个助手入口
5. **DCS 数据**：后台统一接入，前端不暴露配置界面

这个方向是可行的，而且比现在的“Web 仪表盘”更有差异化竞争力。
