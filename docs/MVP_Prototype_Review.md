# 无隅 BizBuddy MVP 原型评价与建议

## 1. 总体评价

这份 MVP 原型已经做到了**必要的减法**：

- 把原本功能很全的“工业智能体平台”收敛成了一个**对话式生产分析助手**
- 只保留一个核心入口（对话）、三个内置专家、两类数据（文档 + 时序）
- 去掉了专家市场、技能库、评估中心、知识图谱等“平台化”功能

这个方向是对的。如果目标真的是 **2～3 个月完成 MVP**，当前范围仍然偏大，但已经是一个可执行的起点。

下面我从**产品定位、功能取舍、技术架构、本地化适配**四个维度展开评价和建议。

---

## 2. 产品定位评价

### 2.1 做得好的地方

- **场景聚焦**：只解决“产线为什么异常”这一个核心问题，而不是做所有事
- **角色明确**：三个专家分别对应工艺、设备、安全环保，符合工业组织分工
- **证据导向**：回答必须带文档引用或 DCS 数据说明，符合工业用户对可信性的要求
- **用户分层**：普通员工和管理员权限分离，DCS 接入不暴露给普通用户

### 2.2 需要再思考的地方

**（1）三位专家是否真的需要“独立存在”？**

从用户角度，用户不会关心“我现在问的是生产分析专家还是设备维护专家”。用户只关心：

> “二号线能耗为什么升高？”
> “这个温度是不是该检修了？”
> “这次作业合规吗？”

建议：
- 把专家做成**隐式的路由/编排**，而不是让用户先选一个专家
- 前端只展示一个统一的“无隅工业助手”
- 后台根据问题自动判断需要调用哪些专家和哪些数据

这样用户心智成本更低，也更像一个真正的 Agent 产品，而不是三个独立的 Chatbot。

**（2）“本地电脑运行”与当前架构的冲突**

你现在的代码是：

- 后端：FastAPI + PostgreSQL（pgvector）+ SQLAlchemy
- 前端：Vue 3 + Vite
- 认证：与 `rswaste-platform` 共用一个 buildingai 用户库
- 向量库：独立的 `gufei_vec` PostgreSQL 库（端口 5440）
- 模型：OpenAI 兼容 API（默认走外网）

这套架构是**典型的 SaaS/服务端架构**，不是“跑在用户本地电脑中的 Agent 类产品”。

## 3. 功能取舍评价

### 3.1 保留的功能是否合理？

| 功能 | 评价 |
|------|------|
| 对话 + 专家选择 | 基本合理，但建议专家选择后台化 |
| 文档上传 → RAG | 合理，且已有实现基础 |
| DCS 后台统一接入 | 合理，符合企业 IT 管控逻辑 |
| 模型配置（管理员） | 合理，本地部署时尤为关键 |
| 轨迹观测（管理员） | 合理，是 Agent 产品的必要基础设施 |

### 3.2 被砍掉的功能是否应该完全砍掉？

| 被砍功能 | 建议 |
|----------|------|
| 知识图谱 | **不要完全砍掉，只砍掉“图谱可视化”**。底层仍需要实体-关系数据支撑检索和推理 |
| 评估中心 | **不要完全砍掉，改成轻量日志 + 人工评分**。否则没有迭代依据 |
| 技能库 | **不要完全砍掉，改成内置 skill 包**。你后面要做 open skill 接入，底层仍然需要 skill 抽象 |
| 专家团 | 合理砍掉，MVP 不需要多专家协作编排 |

## 4. 技术架构评价与本地化适配建议

这是最关键的部分。你现在的架构如果直接搬到本地电脑，会有以下问题：

### 4.1 数据库依赖太重

当前使用：
- PostgreSQL（业务库）
- PostgreSQL + pgvector（向量库）
- PostgreSQL（认证库，与 rswaste-platform 共用）

本地部署问题：
- 普通用户的电脑上不会装 PostgreSQL
- 即使装了，也无法访问企业内部的 `rswaste-platform` 认证库
- pgvector 对本地环境要求较高

**建议**：

| 组件 | 云端方案 | 本地 MVP 建议 |
|------|----------|---------------|
| 业务数据库 | PostgreSQL | **SQLite** |
| 向量库 | PostgreSQL + pgvector | **Chroma / SQLite-vec / DuckDB-VSS** |
| 用户认证 | 与 rswaste-platform 共用 | **本地账号 / 设备密码 / 无需登录** |
| 文件存储 | 数据库 BLOB | **本地文件夹 + SQLite 索引** |

具体来说，可以：

1. 把 `db/client.py` 中的 `engine = create_engine(settings.database_url)` 改成支持 `sqlite:///local.db`
2. 把向量检索从 pgvector 迁移到 `Chroma` 或 `sqlite-vec`
3. 把 `auth_engine` 移除，改为本地简单密码或设备信任

### 4.2 模型调用依赖外网

当前默认使用 OpenAI API 或 DeepSeek API，需要外网连接。

本地部署问题：
- 很多企业内网无法访问外网
- 即使能访问，客户也不愿意把生产数据传到云端

**建议**：

1. **支持本地推理引擎**：
   - 通过 `Ollama`、`LM Studio`、`llama.cpp` 调用本地大模型
   - 后端把 `openai_base_url` 指向本地端口（如 `http://localhost:11434/v1`）

2. **支持双模式**：
   - 云端模式：使用客户提供的 API Key
   - 本地模式：使用本地部署的开源模型（如 Qwen、Llama 等）

3. **模型配置页**：
   - 原型的“模型配置”页面可以保留，但字段需要调整：
     - 本地模型路径 / 服务地址
     - 模型类型：云端 API / 本地推理
     - 并发限制（本地显卡资源有限）

### 4.3 前后端分离不适合本地部署

当前前端是 Vue 3 + Vite 开发服务器，后端是 FastAPI。

本地部署问题：
- 用户需要同时启动两个服务
- 跨端口访问、CORS、进程管理都很麻烦

**建议**：

1. **单进程整合**：
   - 用 `FastAPI` 直接托管前端静态文件
   - 或用 `Tauri` / `Electron` 打包成桌面应用，内部启动 FastAPI 服务

2. **更简单的方案**：
   - 用 Python 写一个单文件本地服务器（如 `fastapi` + `uvicorn`），同时托管 `/api` 和 `/` 静态资源
   - 前端构建产物（`frontend/dist`）作为静态文件由后端直接返回

### 4.4 DCS 数据采集不适合本地电脑

DCS 数据接入通常需要：
- 在工厂内网部署
- 访问 OPC UA / Modbus / MQTT 网关
- 持续运行采集服务

这和“跑在用户本地电脑”是冲突的。如果 DCS 数据要进产品，更合理的做法是：

1. **本地电脑只做分析终端**，不做数据采集
2. DCS 数据由企业内部服务器统一采集和存储
3. 本地电脑通过内网 API 访问企业时序数据库
4. 或者，MVP 阶段直接用 CSV / Excel 文件导入历史数据，不做实时采集

## 5. 本地化架构建议

如果你真的要做一个“跑在用户本地电脑中的 Agent 类产品”，建议架构调整为：

```
┌─────────────────────────────────────┐
│  本地桌面应用（Tauri / Electron）     │
│  ├── 前端 UI（React/Vue 静态页面）    │
│  └── 内置 Python 服务（FastAPI）      │
│       ├── SQLite 业务数据库           │
│       ├── Chroma / SQLite-vec 向量库 │
│       ├── 本地文件存储（documents/）   │
│       ├── Ollama / OpenAI 兼容接口   │
│       └── RAG + Agent 执行引擎        │
└─────────────────────────────────────┘
              │
              ▼
┌─────────────────────────────────────┐
│  企业内网（可选）                      │
│  ├── 时序数据库（InfluxDB/TSDB）      │
│  └── 业务系统 API（DCS/MES/LIMS）     │
└─────────────────────────────────────┘
```

关键决策点：

| 决策 | 建议 |
|------|------|
| 是否必须有 DCS 实时数据？ | MVP 可以先用 CSV 导入历史数据，验证分析价值 |
| 是否必须有外部 LLM？ | 支持本地 Ollama 优先，云端 API 作为备选 |
| 是否必须多人协作？ | 本地单机先跑通，后续再考虑同步 |
| 是否必须做知识图谱？ | 先用文档向量检索 + 规则路由，后续再引入图谱 |

## 6. 对原型的具体修改建议

### 6.1 对话页

- **建议移除专家选择器**，改为统一入口
- 输入框 placeholder 改为：「询问产线、设备或安全环保问题…」
- 回答中明确标注证据来源类型：文档 / 时序数据 / 计算结果

### 6.2 专家页

- 改为「能力介绍」页，而不是三个独立专家卡片
- 展示系统能做什么：
  - 生产异常分析
  - 设备状态诊断
  - 安全环保检查
- 每个能力给 2～3 个示例问题

### 6.3 数据库页

- 保留「文档数据」
- 增加「时序数据导入」Tab：
  - 支持上传 CSV / Excel
  - 显示已导入的数据集
  - 字段映射（时间列、指标列、设备列）

### 6.4 系统设置页

- 模型配置：支持本地 Ollama / 云端 API 切换
- 存储路径：显示本地文档和向量库存放位置
- 企业连接：配置内部 DCS 数据服务地址（可选）

---

## 7. 总结

这份 MVP 原型在**产品收敛上做得很好**，已经具备了可执行性。但如果你真正想要的是**“跑在用户本地电脑中的 Agent 类产品”**，那么当前的技术栈还需要做一次关键的本地化改造：

1. **数据库轻量化**：PostgreSQL → SQLite + Chroma
2. **模型本地化**：支持 Ollama / 本地推理
3. **前后端一体化**：FastAPI 托管静态页面，或打包成桌面应用
4. **DCS 解耦**：本地只做分析，不做实时采集；数据通过 CSV 或企业内网 API 进入

建议下一步先回答三个问题：

1. 产品最终形态是 **Web 应用** 还是 **桌面应用**？
2. 客户是否允许 **联网调用云端 LLM**？
3. MVP 阶段是否必须接入 **实时 DCS 数据**，还是先用 **历史数据文件** 验证？

这三个问题的答案会决定技术路线。
